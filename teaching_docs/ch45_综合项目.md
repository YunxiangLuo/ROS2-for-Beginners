# 第45章 综合项目：城区自动驾驶

> **课程**：ROS2 Python 编程  
> **章节**：第45章  
> **课时**：2 课时（90 分钟）  
> **教学方式**：讲授 + 演示  

---

## 学习目标

本章学习目标包括：综合运用第36~44章所学知识完成城区自动驾驶综合项目，掌握自动驾驶系统架构设计与模块接口定义的方法，理解安全监控与故障处理机制，并按照验收标准完成系统评估与演示。

## 45.1 项目目标与场景描述

### 45.1.1 项目目标

本综合项目要求学生综合运用第36~44章所学知识，在CARLA仿真环境中实现一个完整的城区自动驾驶系统。项目面向真实自动驾驶研发流程，涵盖传感器驱动、感知、定位、规划、控制、安全监控六大模块。

**核心目标**：在CARLA Town03地图中，控制自车从起点A（坐标 `[-80, -10, 0]`）自动驾驶至终点B（坐标 `[130, -120, 0]`），全程约1.8km，包含6个红绿灯路口、3处人行横道、动态交通流场景。

### 45.1.2 场景描述

| 要素 | 描述 |
|------|------|
| **地图** | CARLA Town03（城区道路网格，含双向车道、环形交叉口） |
| **天气** | 晴朗正午（默认天气），可选挑战：雨天、黄昏 |
| **交通参与者** | 10~20辆NPC车辆（随机行驶），3~5名NPC行人（随机穿越） |
| **红绿灯** | 6组信号灯，周期15~30秒随机 |
| **起点→终点** | A `[-80, -10, 0]` → B `[130, -120, 0]` |
| **限速** | 30 km/h（城区道路） |
| **自车** | Tesla Model 3（配备传感器套件） |

### 45.1.3 传感器配置

| 传感器类型 | 安装位置 | 参数 |
|-----------|---------|------|
| 前置RGB相机 | 前挡风玻璃 | 1920×1080, 90° FOV |
| 前置深度相机 | 前挡风玻璃 | 1920×1080, 90° FOV |
| 前置语义分割相机 | 前挡风玻璃 | 1920×1080, 90° FOV |
| 4个环视相机 | 前后左右 | 1280×720, 120° FOV |

| 速度计 | 车轮 | 车速, 里程 |

### 45.2.3 数据流时序

数据流以固定时序在模块间流转：传感器驱动层以 20Hz 频率采集原始数据并发布；感知模块以 10Hz 频率处理图像与点云，输出障碍物、车道线、交通灯与占据栅格；定位模块以 20Hz 频率融合 GNSS、IMU 与车速，输出高频率位姿估计；规划模块以 10Hz 频率接收感知与定位结果，生成 5 秒前瞻轨迹（50 个路径点、0.1s 间隔）；控制模块以 50Hz 频率运行，计算油门、刹车与转向控制量；安全监控模块则独立运行，以 50Hz 频率检查碰撞风险，必要时覆盖控制信号。

### 45.2.4 官方 Capstone 范式：从感知到控制的完整闭环

CARLA 官方文档把综合项目定义为「仿真即验证平台」：官方示例项目（如 Autonomous Driving with ROS 工作流、Leaderboard 评估体系）均要求完整闭环——传感器驱动、感知、规划、控制四个模块同时运行，并用官方指标（路线完成率、违规次数、碰撞/停车罚时）统一验收。本章 45.2.1 的软件栈就是这一范式的简化版：官方强调模块间只通过消息接口通信、任何模块不得直接读取其他模块内部状态，这正是 45.2.3 数据流时序设计的依据。The Construct 的《Self-Driving Car with ROS》课程采用同样的四阶段做法：先让车跑起来（控制）、再理解环境（感知）、再决策（规划）、最后集成调试，与 45.4.1–45.4.4 的迭代顺序一一对应。

### 45.3.2 坐标帧约定

| 坐标系 | 原点 | 说明 |
|--------|------|------|
| `map` | 地图原点 | 全局地图坐标系（ENU右手系） |
| `odom` | 自车起始点 | 里程计坐标系 |
| `base_link` | 后轴中心 | 自车本体坐标系（前x左y上z） |
| `camera_front` | 前置相机光心 | 相机坐标系（z向前x向右y向下） |
| `lidar` | LiDAR中心 | LiDAR坐标系 |

帧变换树：
```
map → odom → base_link → camera_front
                       → lidar
                       → gnss_antenna
                       → imu_link
```

### 45.3.3 模块间依赖契约

模块之间必须遵守五条硬性依赖契约。其一是输入数据保证：传感器驱动必须在节点启动后 2 秒内开始发布有效数据。其二是输出频率保证：每个模块的输出频率不得低于约定值的 80%。其三是时间戳规范：所有消息使用共同的 ROS 时间戳，数据融合时时间差不得超过 100ms。其四是异常处理：模块检测到输入数据超时（>500ms）时，必须发布诊断警告并保持最后有效输出。其五是坐标系一致性：所有空间数据必须附带 `frame_id` 字段，且值与 45.3.2 节一致。

### 45.3.4 工程化组织：launch、日志与模块边界

综合项目规模大，ROS 2 官方文档给出工程化建议：所有节点收敛进统一 `launch` 文件（参数化启动、按键切换自动驾驶/手动模式、`lifecycle` 节点管理启动顺序——传感器就绪后再激活感知），日志用 `ros2 doctor` 体检 + `rqt_console` 分级过滤，调试用 `ros2 topic echo` 定点定位「断点在哪一层」。官方还强调「每个节点一个包、接口单独一个包」的仓库结构（对应 45.3.1 话题接口协议），并建议把 bag 录制脚本与 `all_launch.py` 一并提交——复现实验比写出代码更重要，这与 45.5.5 演示验收流程的「一键启动」要求直接对应。

### 45.3.5 接口契约与分阶段交付的实践检验

Udacity 自动驾驶纳米学位的 Capstone 项目（开源路线）是本章验收标准的最直接来源：其项目说明要求先写接口契约（话题名、消息类型、帧），再对照契约逐模块实现，最后用官方测试（障碍物检测评测脚本、路径跟踪误差阈值）替代人工评判。Udacity 的实践结论与 45.3.3 模块间依赖契约一致：先约定「路径点数组发布频率」「控制指令上限」等硬性协议，模块之间可以各自独立开发、mock 联调；其评分表也分「功能分 + 鲁棒性分」，与 45.5.1 必达指标 + 45.5.3 加分项的结构相同。

## 45.4 迭代开发流程

### 45.4.1 阶段1：路径跟踪（基础能力）

**目标**：实现从起点到终点的路径跟踪，不处理动态障碍物。

**子任务**：本阶段依次完成六项任务——启动 CARLA Town03 并配置 Tesla Model 3 传感器套件；实现传感器驱动节点，验证所有传感器数据正确发布；实现基于 GNSS+IMU 扩展卡尔曼滤波融合的定位节点；实现基于车道中心线生成的全局路径规划；实现纯跟踪（Pure Pursuit）横向控制器与 PID 纵向控制器；最后调试 PID 参数，使车辆在直道上的跟踪误差小于 0.3m、弯道上小于 0.5m。

**交付物**：车辆能够从 A 点平稳行驶到 B 点，平均速度不低于 15 km/h，最大横向误差不超过 0.5m。

### 45.4.2 阶段2：避障（动态能力）

**目标**：在阶段1基础上增加静态和动态障碍物检测与规避。

**子任务**：本阶段在阶段 1 的基础上增加障碍物感知与规避能力，依次实现基于 LiDAR 的障碍物检测（地面分割→聚类→包围框拟合）、基于视觉的车道线检测（语义分割→车道线拟合）、局部占据栅格地图，以及车道保持→减速跟随→停车等待→变道绕行的行为规划与基于 Frenet 坐标系的运动规划，最后验证碰撞率为 0（包括静态障碍物和动态 NPC 车辆）。

**交付物**：车辆能够避开道路上的静态障碍物，能够跟随前方慢速车辆（保持不少于 2 秒的跟车时距），且碰撞次数为 0。

### 45.4.3 阶段3：交通灯（交规遵守）

**目标**：在阶段2基础上增加交通灯检测与红绿灯遵守。

**子任务**：本阶段增加交通灯检测与交通规则遵守，依次实现基于视觉的交通灯检测（YOLO 或颜色分割识别灯色）、交通灯与车道的关联（确定当前车道对应的信号灯）、红灯停车逻辑（提前 30m 减速，距停止线 3~5m 准确停车）与绿灯/黄灯通行逻辑，并处理多路口连续交通灯场景。

**交付物**：红灯停车率达到 100%，停车位置距停止线小于 1.0m，绿灯通行不犹豫，黄灯期间若已越过停止线则继续通行。

### 45.4.4 阶段4：完整闭环（系统集成）

**目标**：集成所有模块，实现完整的城区自动驾驶闭环。

**子任务**：本阶段完成系统集成与全链路闭环，依次集成碰撞预警、偏离预警、紧急制动等安全监控模块，实现系统状态诊断与健康检查，通过 ROS bag 录制关键话题完成完整数据记录，进行传感器降级（模拟某传感器失效）的鲁棒性测试与白天/黄昏/雨天、小/中/大交通流量的多场景验证，最后优化端到端延迟（≤150ms）与各模块 CPU 占用。

**交付物**：完整系统在标准场景下稳定运行，所有验收指标达标，并提交完整的代码、配置文件、启动脚本和测试报告。

### 45.5.5 演示验收流程

演示验收依次分为五个环节：首先进行 15 分钟的代码审查，评审核心模块代码，检查架构合理性和代码质量；随后用 5 分钟运行一键启动脚本，验证系统正常启动；接着进行 10 分钟的标准测试场景运行，实时观察系统行为；再用 5 分钟通过 ROS bag 回放关键数据，验证各模块输出；最后安排 10 分钟的问答环节，回答评审人关于系统设计和实现的问题。

### 45.5.6 验收文化：评分表驱动的演示与复盘

The Construct、Udacity 等国际课程都强调「项目以演示结束」：演示要有固定脚本（场景、操作步骤、预期现象），录制视频留存，复盘时先看失败的场景分类（感知漏检/规划卡死/控制超调）再定位模块。CARLA 官方 Leaderboard 与 ScenarioRunner 则提供量化验收：相同场景、相同配置下的成绩可横向比较，官方建议把「多次运行统计」而非「单次运气」作为验收依据。这与 45.5.5 演示验收流程的评分构成一致——把主观演示变成可重复的量化评价，正是本章综合项目想让你养成的最后一项工程习惯。
